# V4.2 每日连载：先检查，后定稿

目标是每天创作并发布一章，已发布内容无法回改。作者面对一个GPT；同一个GPT依次规划、写作、审阅和保存。日常指令见《每日一章指令.txt》。本系统降低长篇失控风险，不保证作品完美、读者留存或平台签约。

## 定稿与发布分开

| 状态 | 允许 | 边界 |
|---|---|---|
| 候选 | 完整初稿登记后最多三轮局部修订 | 半章、检查未过稿不能计入定稿 |
| 定稿冻结 | 阅读、复制、导出 | adopt同时锁正文和事实记录，不再edit/repair/revalidate |
| 平台已发布 | 有真实回执或作者明确确认后publish | 导出、GitHub可见、预约时间均不等于发布成功 |

新书bootstrap默认serial_mode=true。旧书完成已授权修改、候选和影响核对后serial-enable；仅冻结已有版本，不追认开篇检查或平台发布。无回执称“未登记”，不推断一定没发布。工具防止常规流程误改，不是防管理员恶意篡改的安全系统。不得手改state、删除冻结清单、重初始化或降级绕过；没有日常解锁入口。

## 开书先确定因果与结局

先选择平台、核查现行官方规则和近期榜单、给5—10个原创选题，等作者选择。选定后canon写持续愿望、人物信息边界、能力和不可恢复代价、世界硬边界及故事时间；roadmap写全书主冲突、阶段因果和结局条件，当前阶段细化，近期三章滚动。未来安排不是已发生事实。

开篇默认采用下列编辑检查线，第一章定稿前可按题材和作者要求配置。它们不是平台硬规定，也不是转化率公式。

| 正文汉字实测位置 | 必须实际呈现 |
|---|---|
| 800字内 | 具体异常、冲突、欲望或人物处境，形成继续阅读的理由 |
| 3000字内 | 与书名和题材相符的实际场面，不能只写预告 |
| 3000字内 | 事件触及主角的利益、恐惧、选择或关系 |

opening.first_hook/core_promise/protagonist_impact填真实引文和判断理由，程序计算位置。倒叙须明确回到何时，事实时间按真实发生顺序，不让人物提前知道后来的信息。不能用重复预告、梦境或脱离正文的爆点骗过检查。第2、3章在promises检查中核对早期承诺是否开始兑现一个答案、成果或关系变化；大谜团可留后面。不强制每章生死悬念，也不把设定解释塞满开头。

## 每章定稿前的顺序

1. 读远程头、state、workflow和接管记录，续未完任务，不重开或跳章。读canon、roadmap、上章和最近三章全文、五章推进及本章相关旧来源；到期回看提前分批读完整范围。
2. 核对人物地点、故事时间、知情者、钱与资源、伤损、能力边界、承诺到期和旧错。明确本章一个主要改变及不能撤销的后果，再确认后续三章接得住。多思考不能替代外部记忆与原文回查。
3. 完整写作、candidate登记、一次集中检查，必要时repair。同一任务最多三轮，不换任务清零。超限保留候选与证据，处理未定稿结构，不为赶日更采用已知矛盾。
4. release-request只生成pending模板。GPT实际阅读后填八项检查：时间、知情、物资、因果、能力、承诺、重复、人物主动性，每项有版本和原文。与最近三章逐章比较办法、选择和后果，不能只换机关名。写本章实际代价、继续阅读理由、结尾篇幅，以及未来三章的目标、改变和待解问题。
5. 每第五章采用前，读当前候选加前四章全文；每十章、实际阶段收束章和最后一章采用前，读当前阶段全部正文。准确覆盖正文与记录哈希。阶段提前结束，在本章记录设stage_closing=true触发提前阶段回看；跨阶段仍要求上一阶段有效stage报告。不能先冻结第十章再要求回改。
6. release-check通过才adopt，同时保存正文、语义记录、冻结版本、承诺及到期回看。报告绑定book_id、revision、候选任务、修订次数、正文、语义记录、canon、roadmap；任何一项改变重新检查，不复用旧报告。
7. 更新接管、workflow和online/index并校验；以当前远程头非强制提交、回读。导出给作者发布。实际看到发布依据再publish并同步。一天一章是执行目标，网页不自动向七猫投稿，也不无人值守写作。

程序核查结构、版本、引用、覆盖和状态，不能证明GPT真的阅读全文，不能判断引文足够、动机合理或作品好看。报告需保存具体判断，不得脚本批填“通过”。

## 避免长篇失控

**承诺不无限延期。** 从实际thread_events投影开放问题，promise_reviews逐项给到期章。普通推进和partial不重置期限。提前调整用reschedule，到期失约用miss，必须有本章真实原因、代价、引文和新期限，历史不删。到期未处理会拦截下一章。大谜团可设远期终点，短期承诺拆子项；开放结局也要close明确交代，不能假装问题全答完。

**后果只向前。** 不让伤瞬愈、旧债重还、死者无据复活、已花资源回满、限制临时消失。对白声称、belief、knowledge与fact分开。材料、能力要有独立来源和实际试验，未来计划不写进事实。

**阶段必须有结果。** 回看检查主目标是否变化、是否给答案、主要办法是否循环、对手是否行动、关系是否通过选择改变。长期只加纸条、门或下一次检查而不改变处境，就调整未来路线，安排见人、承担损失、交付结果和面对后果。不能靠新反派、改规则或清零旧胜利凑篇幅。

**结尾提前准备。** 每章填ending_runway；第25/50/75/90章及阶段末按实际字数、开放承诺与必要场面重估。最后十章优先兑现，唯一解法必须提前建立来源与代价。90万字与故事成立冲突时，给作者具体篇幅方案，不自动灌水或偷改总目标。

**旧错只前向处理。** incident保存原章哈希、引文、矛盾、影响、前向方案与目标章。后续release逐项contain或resolve，用当前正文证据支持；未解决保留下一目标及历史。可以承认误判、承担损失、补足已有因果；不能新增“早就知道”“其实没死”或万能规则抹平事实。没有诚实可行的补救时保留具体阻断，不保证式圆谎。

## 工具入口

由GPT操作，作者不填JSON。所有路径和版本取当前实际值。

```bash
python tools/novel_state.py --root book release-request --text drafts/CH001.txt --record drafts/CH001记录.json --out drafts/CH001发布前检查.json
# 实际阅读和填写；有问题先repair，重新绑定版本
python tools/novel_state.py --root book release-check --text drafts/CH001.txt --record drafts/CH001记录.json --report drafts/CH001发布前检查.json
python tools/novel_state.py --root book adopt --text drafts/CH001.txt --record drafts/CH001记录.json
python tools/novel_state.py --root book status
# 仅有真实发布依据后填写实际哈希、带时区时间及确认原话或回执
python tools/novel_state.py --root book publish --chapter 1 --text-sha256 实际哈希 --published-at 实际ISO时间 --evidence 实际发布依据
# 旧书完成核对后迁入；不是新书bootstrap替代入口
python tools/novel_state.py --root book serial-enable --base-revision 实际版本 --reason 作者要求建立定稿冻结基线
python tools/novel_state.py --root book incident --report drafts/旧错前向处理.json
```

未启用serial_mode的旧工程才保留edit/revalidate迁移路径。冻结后本规则优先，reopen不解冻旧章。新聊天须读取真实文件，不只凭提示词记忆续写90万字。

迁入已有作品时，可用`serial-plan --report 计划文件.json`一次补齐尚无期限的全部开放项；报告含base_revision、roadmap_sha256及plans（每项id、deadline_chapter、reason）。已有期限禁止用此入口覆盖，后续必须在真实新章审查中记录调整与代价。资料包默认预算80000字符，超出须分批读并保留范围；不是token额度，也不自动证明当前模型装得下。
